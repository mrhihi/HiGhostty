狀態：設計提案，尚未實作。依 2026-10-15 工作目錄內的程式碼分析，包含尚未提交的功能；本文不代表這些功能都已完成實機驗收。

可直接拆工作包的實作合約見 [專案區實作規格 v1](project-implementation.md)，包含型別、儲存交易、CLI/IPC、狀態機、派送演算法與逐檔修改。兩份不同處以實作規格為準。

## 1. 產品定位與已確認界線

在左側工作區上方增加「專案」區。每個專案對應一個目錄，以目錄內 `.highostty/` 保存設定、計畫與協作紀錄。點專案預設進入與專案相關的 agent 狀態首頁。

專案有自己的協調 agent。人與它討論計畫，它向其他頁籤的 agent 委派工作、接收回覆、整理交接與追蹤結果。

**其他頁籤能做什麼、可以使用哪些工具、需要哪些核准，全部由該頁籤的 agent 決定。** 專案不建立 Mail/Jira 權限表、不修改其他 agent 的設定、不替其他 agent 回答工具授權。對方提供的能力說明只用於安排任務，不是專案授予的權限。

例如 Mail agent 說自己只能讀信，專案就向它要求讀信與整理資料；Jira agent 是否能建立議題、何時需要人核准，由 Jira agent 自己處理。專案接收「已完成／拒絕／需要人／缺資料」並調整計畫。

## 3. 導覽與首頁

建議「工作區上面」定義為現有工作區 Drawer 內的上方分區，方便同時看到專案和原有頁籤。

```text
Rail │ 工作區                         │ 客戶需求整理                     ⋯
     │ 專案                       ＋  │ [總覽] [計畫] [任務] [紀錄] [設定]
     │ ● 客戶需求整理       1 待處理  │
     │ ○ 發版準備                   │ 待你處理：Jira agent 需要確認分類
     │ ────────────────────────   │
     │ 工作區                     │ 相關 agents
     │   Mail                     │ Mail   整理信件中    [查看終端機]
     │   Jira                     │ Jira   等待資料      [查看終端機]
     │   其他終端機…              │
     │                            │ 目前計畫：讀信 → 整理 → 建立 Jira
     │                            │ 最近成果：需求摘要 v2
     │                            │ ──────────────────────────────
     │                            │ 專案 agent：正在等待 Mail 回覆
     │                            │ [討論計畫／輸入工作要求……] [送出]
```

### 首頁內容與優先序

1. 待人處理事項：問題、來源 agent、影響的任務、前往處理。
2. 相關 agents：名稱、用途、連線狀態、終端觀測狀態、目前專案任務、最近回報時間。
3. 目前計畫：版本、執行進度、下一步、暫停／繼續。
4. 最近成果：摘要、文件與外部連結，例如 Jira 單號及對應信件來源。
5. 專案 agent 討論區：討論計畫、追問結果、提出修改。

首頁列出所有已關聯成員，已開啟者在前，未開啟者顯示「未開啟」及「開啟」。跨視窗成員也顯示；純 shell 顯示「尚未偵測到 agent」。未加入的終端機不自動列入。

### 點擊與切換

- 點專案名稱：一律進總覽，不因之前看過終端機而直接切到 coordinator。
- 點 agent 卡片：開任務與回報詳情；「查看終端機」才切到該頁籤、聚焦正確分割。其他視窗的頁籤則帶出對應視窗。
- 從專案前往終端機：顯示「返回專案」入口；若成員屬於多個專案，返回此次來源，不猜測。
- 點工作區頁籤：維持現在的終端機行為。專案與頁籤各自記住捲動位置和選取內容。
- 專案清單可收合、排序；列上的數字表示未解決事項數，不把所有 blocked agent 都算成一筆。
- 第一版不改 ⌘1～⌘9 頁籤順序。專案畫面的 ⌘W 關閉專案檢視並回到上一個內容，不終止背景 agent；⌘T 在專案根目錄開新終端機並切過去（不自動加入成員）。
- 專案首頁的輸入框只把文字交給 coordinator，不直接輸入任何 worker 終端機。中文組字中的 Enter 不送出。
- 窄視窗改為單欄，討論區可切換展開；右側詳情改為主內容子頁，保留返回路徑。

## 4. 建立專案與關聯 agent

### 建立流程

1. 點「專案 ＋」→ 選擇既有目錄，或先建立新目錄。
2. 填名稱，預設目錄名稱。若已存在 `.highostty/project.json`，提供「開啟既有專案」。
3. 選專案 agent 種類、啟動參數、是否使用 tmux；預設工作目錄為專案根目錄。憑證仍由 agent 自己管理。
4. 可勾選目前開啟的 agent 作為成員，也可先略過。清單顯示視窗、頁籤、分割位置、cwd、agent 種類，避免同目錄同名選錯。
5. 顯示建立摘要；按「建立並開啟」才建立 `.highostty/` 與啟動 coordinator。讀到既有專案設定不自動執行其中的啟動命令。
6. 進首頁；coordinator 啟動或信任詢問未完成時，首頁仍可使用，顯示啟動狀態及「前往終端機」。

建立完成不自動啟動全部成員或派送任務。重新點已開啟的專案不重建 coordinator。

### 成員關聯

- 成員代表一個穩定的合作對象，實際派送定位到 terminal surface；同頁籤的兩個分割可有兩個成員。
- 從首頁「加入 agent」選開啟中的 agent，或選擇收藏／目錄與啟動方式作為之後的開啟入口。
- cwd 只協助找候選，不決定成員身分。成員 `cd` 後仍維持關聯。
- 同一成員可供多個專案使用；UI 顯示正在服務的專案，派送共用同一個佇列，避免互相插話。
- 「了解用途」會詢問對方 agent 可協助什麼及回報方式，回覆附時間與來源。人也能先填用途備註。對方可以不支援結構化回報，顯示「畫面追蹤」。
- 「移除成員」移除專案關聯，不關閉終端機；若有進行中任務，先顯示受影響任務並選擇保留追蹤或停止後續派送。
- 「開啟成員」只啟動使用者指定的入口，保留其既有 agent 設定；專案不替它安裝或改寫 Mail/Jira 工具。

## 5. 人與專案 agent 怎麼寫計畫

輸入「整理上週客戶來信，把需要處理的項目交給 Jira agent 建單」。coordinator 先釐清不足的條件，例如客戶、日期範圍、何謂需要處理，並了解可用成員。已經明確的條件不重複詢問。

計畫是可保存的文件加結構化任務，包含：目標、範圍、負責成員、輸入、預期成果、相依步驟、交接內容及完成條件。

| 階段 | 畫面與操作 | 執行規則 |
| --- | --- | --- |
| 草稿 | 討論區提出計畫，計畫頁可讀完整版本 | 討論與修改不自動派工 |
| 待開始 | 顯示每步負責者與交接摘要，「開始執行」 | 若人已明確說直接執行，記錄該授權後開始，不再增加重複確認 |
| 執行中 | 任務逐步更新，討論仍可進行 | 只派送已符合依賴且在目前執行範圍的任務 |
| 計畫修改 | 顯示差異和受影響的步驟 | 未派送任務採新版；已送出任務不能假裝撤回，另記變更要求 |
| 完成 | 顯示成果、來源與未解事項 | 以任務成果及完成條件判定，不能只看 agent 變 idle |

「開始執行」表示同意專案依這份計畫委派工作，不代表替各 agent 通過其工具授權。既有計畫範圍內的後續步驟可自動交接，不要求每一步再按一次同意；超出範圍的調整才回到人與 coordinator 討論。

第一版建議：人用文字與 coordinator 討論，agent 經專案指令提交計畫版本，由 UI 提供版本差異與開始按鈕。避免同時開放 UI 結構編輯器與 agent 任意寫 JSON，造成兩份計畫。

## 6. Mail → Jira 完整動線

1. **提出要求**：人在首頁輸入目標，或選既有草稿繼續。
2. **擬定計畫**：coordinator 安排 Mail 蒐集、需求整理、Jira 查重及建單；是否查重由要求與 Jira agent 的回覆決定。
3. **開始**：人開始計畫，首頁顯示 Mail 任務派送中，Jira 任務等待上游。
4. **Mail 接收**：任務帶 task ID、具體範圍、所需成果與回報方式。Mail agent 自行處理可讀範圍、登入或授權。需要人時回報阻礙，任務暫停在此。
5. **Mail 交件**：回傳摘要、信件來源識別、需求項目、附件參照、未知或無法取得的資料。專案保存交件版本，不把整個終端 scrollback 當作交接。
6. **整理交接**：coordinator 檢查是否足夠完成計畫，必要時追問 Mail 或人；形成 Jira 任務輸入。首頁可開「交接內容」檢視實際傳給 Jira 的資料。
7. **Jira 接收**：只取得該任務需要的資料、來源與完成條件。它依自己的設定接受、拒絕或詢問，不接收 Mail agent 的憑證。
8. **人處理阻礙**：首頁卡片顯示「Jira agent 需要選擇類型」及受影響任務。前往 Jira 終端機回答；專案不自動按授權鍵。若只是缺業務資訊，也可在專案回覆後由 coordinator 轉達。
9. **結果回傳**：Jira agent 回傳建立／已存在的議題、失敗項目與原因。coordinator 建立「信件 → 需求 → Jira」對照。
10. **收尾**：首頁顯示完成數與未完成數。若 5 筆中成功 3 筆，只對剩餘 2 筆安排後續，不重跑已建單項目。

**成果不足時**：coordinator 可對 result-ready 的任務「退回重做」，同成員建立新 attempt，附上前次成果與修改意見，舊 attempt 保留；不必重做整份計畫。

**worker 回報可能觸發它自己的核准**：回報指令是 shell 呼叫，worker 可能每次都要人核准。握手時請 worker 說明，UI 提示使用者自行在該 agent 允許 `highostty ctl project *`；專案不代為設定。無法執行 shell 的 worker 走畫面追蹤。

資料交接採成果快照加必要摘錄。檔案路徑是輔助參照，若對方無法讀取該檔，由它回報，coordinator 可轉交內容或請人處理；不假設同機上的 agent 都可以讀同一檔案。

## 7. 狀態、派送與回報協定

### 畫面狀態與任務狀態分開

| 層次 | 狀態 | 用途 |
| --- | --- | --- |
| 終端觀測 | working / idle / blocked / unknown / offline | 沿用辨識結果並顯示觀測時間；掃描失敗顯示 unknown，不沿用舊綠燈 |
| 任務 | draft / queued / dispatching / sent / accepted / running / needs-input / declined / result-ready / completed / failed / cancelled / uncertain | 表示專案流程進度；sent 只代表已送出，completed 表示成果符合計畫 |

`idle` 不等於完成、`blocked` 不等於失敗、逾時不等於沒收到。無法觀測或回報時保留「待確認」，不自動宣布成功。

### 任務封包

每次委派包含 `projectId`、`runId`、`taskId`、`attemptId`、`memberId`、計畫版本、目標、輸入快照、成果要求與回報方式。`taskId` 代表工作，`attemptId` 代表本次嘗試；相同 attempt 重複回報不重複套用。

建議回報種類：`accepted`、`progress`、`needs-input`、`declined`、`result`、`failed`。每則回報包含任務、嘗試與訊息 ID，成果可帶摘要、文件及外部單號。只向使用者顯示確實收到的資訊，未接受就不能顯示「已接案」。

新增指令示意（尚未實作，名稱可於 API 設計階段收斂）：

```text
highostty ctl project current
highostty ctl project members <project-id>
highostty ctl project plan submit <project-id> --file <path>
highostty ctl project task dispatch <project-id> --file <path>
highostty ctl project task report <task-id> --attempt <id> --file <path>
```

純查詢維持 `write:false`；提交計畫、派送、保存回報均改動持久資料，應標 `write:true`。沿用目前全域控制模式，UI 要明確顯示 readonly 時可看狀態但不能經 ctl 自動派工或保存回報。這是 HiGhostty 的控制介面限制，不是 Mail/Jira 工具權限。

### 派送佇列

- 每個實際 agent 執行個體同時只保留一個專案派送中的工作；其他專案排隊，避免把多個 prompt 同時插入。
- 現有 `agent prompt` 可對 working agent 送入文字；新專案派送器要先等適合接收的狀態，不能直接照搬這個寬鬆行為。
- 使用者直接在終端機與 agent 對話優先。能觀察到人工輸入或前景工作時停止派送；無法可靠確認時，保留待派送，讓使用者選「現在交付」。
- coordinator 本身也有收件佇列，worker 回報先保存，再於 coordinator 可接收時通知；不把每次畫面變動都送成新 prompt。
- 等待超時提供「查看終端機／繼續等待／重新綁定」，不自動重送可能已執行的任務。
- 只有畫面追蹤的 agent，coordinator 可整理候選成果，但標示「由畫面整理，待確認」；沒有明確證據時不自動推進需要外部寫入的下游任務。
- `result-ready` 由成果回報產生；coordinator 檢查完成條件後才成為 completed。對外操作回報應附 Jira ID 等可對照證據。

worker 回覆與郵件內容作為任務資料，不能自行變成新的計畫指令。是否增加任務仍依原本目標，由人與 coordinator 決定。

## 8. 討論區與 coordinator 的實作選擇

目前只有終端機 prompt 派送、畫面讀取，沒有共通的 agent 聊天訊息 API。不可直接把 viewport 每次快照當作聊天訊息，否則會重複、截斷並混入 spinner。

建議第一版：首頁有「給專案 agent 的訊息」輸入框、可保存的人類訊息、計畫版本與結構化回報。coordinator 跑在背景終端機，透過新增的專案回報指令提交面向使用者的回覆；「查看專案 agent 終端機」保留完整原始互動入口。未支援回報的 coordinator，先顯示「前往終端機討論」，不呈現假的完整聊天歷史。

因此首頁可以預設是狀態儀表板，又能逐步提供真正的討論介面。後續若需要 token 串流、取消單則訊息與對話恢復，再為各 CLI 增加原生協定 adapter，不在第一版假設所有 agent 都支援相同協定。

```text
    plans/<plan-id>/v1.json    # 結構化計畫，版本建立後不覆寫
    plans/<plan-id>/v1.md      # 給人閱讀的計畫，由同一版本生成
    runs/<run-id>/state.json   # 任務狀態快照
    runs/<run-id>/events.jsonl # 派送／回覆／決策／交接事件
    runs/<run-id>/artifacts/   # 交接與成果快照
```

App 資料目錄另存專案路徑索引、排序、最近開啟位置、視窗與 surface 綁定。可攜設定用相對專案根目錄的路徑；外部成員目錄允許本機覆寫，不把某台機器的絕對路徑當通用設定。

`.highostty` 的「隱藏」只代表 Finder 預設不顯示。建議建立時預設將整個資料夾加入本機 Git exclude，避免郵件摘要、討論與執行紀錄被提交；使用者若要共享計畫，再明確挑選設定和文件。建立摘要顯示此選項，既有 Git 忽略檔只追加必要規則。

不複製 agent 憑證、token 或個別工具設定。專案可設定紀錄保留時間、清理歷史；清理前列出會移除的 runs 與成果，不影響外部 Jira 或原始信件。

## 10. 身分、恢復與異常

- `projectId`、`memberId`、`agentInstanceId` 是穩定識別；surface ID 是本次 app 連線位置。關聯記錄區分收藏啟動模板與實際 instance。
- 使用 tmux 時，受控建立的 session 可作為重新辨識線索；只有 cwd、標題或 agent 名稱相同時，不自動認定為同一 instance。無法唯一確認就讓人重新綁定。
- 一個專案只啟動一個 coordinator instance。第二個視窗開相同專案時顯示同份狀態；派送由 Rust 中央服務序列化，避免兩個 WebView 各派一次。
- 狀態寫入走單一 Rust 儲存服務、版本檢查及暫存後原子替換；同機多執行個體需專案鎖，未取得鎖只讀。events 用序號去重，尾端不完整紀錄可偵測並復原。
- app 重開先載入歷史和未結任務，再重新確認 agent。進行中工作先標「恢復確認中」，不自動重送。tmux 存活只表示程序可能仍在，不表示任務完成。
- 非 tmux agent 已結束時，可重新開啟入口，但需用任務摘要恢復上下文，不聲稱恢復原對話。
- 專案目錄改名或搬移：索引顯示找不到，提供重新定位；找到相同 projectId 後更新。複製出的相同 ID 由人選「原專案搬移」或「建立獨立副本」。
- 目錄唯讀：可檢視現有內容，保存失敗時顯示具體原因並停止新派送，避免做了工作卻無法留下紀錄。
- 關閉專案檢視不停止工作。「暫停計畫」停止後續派送；「請求取消」向相關 agent 提出取消要求，收到回覆前顯示取消中。已建立的 Jira 不因取消而自動撤銷。
- 關閉成員終端機沿用現有確認流程，額外列出受影響任務。移除專案索引不刪目錄、不關閉其他終端機；刪除專案紀錄需獨立操作。
- 尚未解決的任務問題需保存；點進頁籤只清現有提示的未讀，不等於問題已解決。任務問題要靠後續回報或人明確處理才關閉。

## 11. 程式架構與原生版面

建議新增：

| 模組 | 責任 |
| --- | --- |
| `src/projects.ts` | 專案、成員關聯、導覽的純狀態 |
| `src/project-tasks.ts` | 任務依賴、狀態轉移、成果與版本的純邏輯 |
| `src/project-panel.ts` | 首頁、計畫、任務詳情、紀錄、設定 UI |
| `src-tauri/src/projects.rs` | 儲存、索引、鎖、版本、跨視窗事件 |
| `src-tauri/src/project_dispatch.rs` | 中央派送佇列、去重、未結派送恢復，交由 surface 所屬視窗執行 native op |

`main.ts` 現有 `active: Tab` 與大量操作都假設目前內容是終端機。新增 `activeContent = terminal(tabId) | project(projectId)`；保留最近使用的終端機頁籤，並逐一檢查 focus、快捷鍵、檔案面板、預覽、關閉、標題和 session 保存，不以「假的 terminal tab」冒充專案。

專案首頁為獨立 HTML 主內容。切入時原生 layout 送空 rects、將焦點轉到 WebView；終端程序繼續執行及掃描。切回終端機恢復 rects 和焦點。首頁不使用分割樹或全頁 cutout；若之後需要同畫面看 coordinator，必須明確切出專用原生矩形。

原有終端機頁籤仍由原視窗回覆控制請求，即使使用者正在看專案首頁也不能漏回 `control-request`。新增專案命令的路由需定義中央 owner，避免各視窗重複處理持久資料寫入。

## 12. 分階段交付

| 階段 | 交付內容 | 完成條件 |
| --- | --- | --- |
| A：專案與狀態首頁 | 專案區、隱藏設定、明確成員關聯、跨視窗狀態、返回動線 | 點專案不開終端機；worker 可正常切換、關閉與重新綁定；原終端操作維持正常 |
| B：協調與可保存計畫 | coordinator、討論入口、計畫版本、任務依賴、事件紀錄 | 人可討論並開始一份計畫；重開 app 看得到同份計畫與歷史 |
| C：可靠委派與交接 | 中央佇列、結構化接受／回報、成果快照、阻礙處理、恢復 | Mail → Jira 能完成；忙碌、拒絕、超時與部分成功均有明確結果，不重複建單 |
| D：體驗擴充 | 對話 adapter、能力說明更新、搜尋、歷史清理、可重用計畫 | 在可靠流程上改善效率，不擴張成 worker 的權限管理中心 |

A 能先交付可用的專案入口；符合完整需求的第一個版本需要 A+B+C。第一版支援任意目錄與既有 agent，Mail/Jira 是示範流程，不在程式中寫死兩種角色。

## 13. 實作後驗收項目

以下是未來實作需要完成的驗收，本次只規劃，未執行測試或 App 操作。

1. 專案建立／開啟／搬移／重複 ID／唯讀／損壞設定都有明確動線；不自動執行陌生專案的啟動命令。
2. 同目錄多 agent、同頁籤多分割、多視窗、多專案共用成員，都派到正確 instance。
3. 專案頁 HTML 不被 NSView 遮住，切換後焦點、中文輸入、預覽與檔案面板正常；debug/release 都要實機操作。
4. worker 正在工作、等授權、人工對話或離線時，不插入不適當的 prompt；不替 worker 通過授權。
5. 逾時、重複回報、重啟與兩視窗同時操作不造成重複委派；外部寫入不明時先核對成果。
6. 接受、進度、拒絕、缺資料、部分成功、完成都有可見且持久的紀錄；idle 不直接判定成功。
7. 真正完成一次 Mail → Jira：有來源、交接快照、單號對照；Jira agent 自己決定其工具權限。
8. 純狀態模組補相應測試；控制命令、skill 和 OPS 表同步。涉及原生、tmux、預覽、header 或輸入的實作，依 AGENTS.md 先讀相應文件並完成該功能的實機驗收。
